# The A/B task benchmark — frozen protocol

This protocol is fixed **before** the first live-model run, so the experiment
cannot be tuned around its results. Changing any part of it after results exist
requires a new protocol version and a fresh pair of arms.

The question it answers, and the only one it is allowed to answer: **does an
agent with SUTRA enabled still complete the same tasks correctly, and what does
it cost or save in real session usage?** It does not measure compression
percentages (see [benchmark.md](benchmark.md) for those) and it does not
extrapolate cost from bytes.

## Arms

| Arm | State | How |
|---|---|---|
| control | SUTRA disabled | `hermes plugins disable sutra && hermes gateway restart --yes` |
| treatment | SUTRA enabled (defaults) | `hermes plugins enable sutra && hermes gateway restart --yes` |

The runner verifies and records which state was active for every session
(`hermes plugins list`); it never infers the arm from behavior. Nothing else
may differ between arms: same model, same provider, same model settings, same
task prompts, same fixture files, same toolsets, same time budget.

## Task set (frozen, eight tasks)

Deterministic fixtures are generated by `scripts/ab/run.py` into a scratch
workspace (seeded; identical bytes for both arms). Each task has one objective
scorer — a programmatic check on the agent's final answer or on the fixture
workspace, never a judgement about whether the answer "sounds right".

| # | Task | Fixture | Scorer |
|---|---|---|---|
| 1 | find the failing test in a long run | ~6,000-line test log, one FAIL | final answer names the planted failing test |
| 2 | diagnose a stack trace | ~3,000-frame traceback | final answer names the exception type and the planted message token |
| 3 | name the failing assertion's variable | test output with one AssertionError | final answer names the planted variable |
| 4 | report what a patch changes | ~40 KB diff (sized to survive Hermes' terminal cap intact), planted added line | final answer names the planted file and line token (diff is protected — this task must not regress) |
| 5 | find a record in a large JSON response | ~2,000-record JSON | final answer names the planted email value |
| 6 | answer from evidence buried mid-output | log with the answer only in the elided middle | final answer contains the planted clue token |
| 7 | evidence near the elision boundary | log with the answer just inside the kept tail | final answer contains the planted token |
| 8 | make a tiny broken function pass | fixture repo + one failing test | the test command exits 0 in the workspace after the session |

Task 6 is the recovery-dependent task: in the control arm the clue is directly
visible; in the treatment arm it sits where SUTRA elides it, so passing requires
either `sutra_restore` or re-running the tool narrower. Its control/treatment
delta is the headline result, read with the sample size in mind.

## Execution order and repetitions

- Minimum: one full pass per arm (8 tasks × 2 arms = 16 sessions).
- Preferred: two passes with **reversed arm order** (ABBA) to expose drift and
  ordering effects. Task 8 and any task whose first attempt timed out get a
  second attempt, recorded as such.
- Sessions run sequentially; nothing else may use the gateway during a pass.

## Running the runner

From the repository root, with the live plugin already in the arm you are
measuring:

```bash
python scripts/ab/run.py --arm on --out results/ab-pass1
```

`--dry-run` builds the fixtures and records without starting a session and
without probing the host; it is the safe mechanics check before an arm is set.
A live run probes `hermes plugins list` once, before any fixture work, with a
default budget of 120 s. `--probe-timeout SECONDS` overrides that budget and
must be greater than zero. It bounds only the arm-state probe; the per-task
session budget is separately set by `--timeout` (default 900 s).

## Measurements (per session, written to `results/*.json`)

- arm, task, seed, pass index, session id, start/end timestamps;
- provider-reported usage from `session_model_usage` in the Hermes state DB:
  the **sum of every row recorded for the session** (that is what the provider
  billed), kept alongside the main-task row alone so Hermes' own auxiliary
  calls (title generation) remain visible instead of silently mixed in.
  Usage is recorded exactly as reported or marked `null` — never estimated
  from bytes;
- the final assistant answer;
- the objective score (pass/fail + the detail the scorer matched);
- treatment arm only: whether a SUTRA marker appeared in any tool result, how
  many `sutra_restore` calls the session made and their statuses (from the
  transcript in the Hermes session store and `sutra-stats.jsonl`);
- wall-clock duration and any timeout/error, with the deviation recorded in the
  results file (never silently dropped). A session that overruns its budget is
  a **recorded failed session**, not a skipped one; a repeated identical
  recovery call that the host deduplicates is recorded as
  `deduplicated-by-host`, not as a failure.
- arm-state verification is part of the record: the runner parses the plugin's
  status cell from `hermes plugins list` and aborts on a mismatch with `--arm`.
  Validated live on 2026-10-24: disabled → oversized results reach the model
  with no marker; enabled → the full compress/recover loop passes.

## Reporting rules

- Report both arms per task and in aggregate; never report only the treatment.
- No conclusion from a single pass; state the sample size with every number.
- A task the control arm fails is reported as an invalid task (bad fixture or
  prompt), not a treatment success.
- Token savings are stated only from provider-reported usage deltas, per task,
  with the caveat that prompt caching makes re-sent context cheaper than raw
  token counts suggest.
- If the provider reports no usage, the experiment reports task success and
  recovery behavior only, and says so.

## Amendment record

Changes after freezing are listed here; the scorers, fixtures, task set and
order are frozen and may only change with a new protocol version (and fresh
arms) once results exist.

- 2026-10-25, pre-first-run (mechanics): the runner aborts when the target
  results file already contains records, so a re-run can never silently mix
  stale and fresh observations in one file. No scorer, fixture, task or order
  changed. (No results existed when this landed.)
- 2026-10-24, pre-first-run (execution/reporting audit): per-arm/pass record
  files; usage summed across the session's rows with the main-task row kept
  separate; host-deduplicated restore calls classified; timeouts recorded as
  failed sessions; arm-state parsing made exact and live-validated; report
  generator added (`scripts/ab/report.py`). No scorer, fixture, task or order
  changed.

## What this protocol deliberately does not do

- No scoring by plausibility; no model-judged grading.
- No concurrency; no cherry-picking sessions after the fact; every started
  session appears in the results, pass or fail.
- No claims about tasks outside the frozen set.
